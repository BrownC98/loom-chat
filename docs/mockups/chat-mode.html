loom 채팅 모드: 타당성 검토와 화면 목업

사람 요청(2026-11-19): “loom에 chat 모드 추가했으면 한다. 에이전트간 통신과 loom 외부와의 통신도 chat 형태로 보이는 기능을 추가하고 싶음, 중간에 사람이 개입도 가능하게, 현실성 따져보고 목업 만들어봐”. 기존 DB와 채팅방 구조를 조사한 결과, 새 저장소를 복제하지 않고 1차 웹 버전을 2.5~4일 규모로 구현할 수 있습니다. 아래에 타당성 근거와 두 화면 시안(D1-A·D1-B), 결정 사항 4건(D1~D4)을 정리합니다.

타당성 검토 요약 코드베이스 실측 근거

구현 가능 · 1차 웹 2.5~4일 에이전트 간 메시지(messages)와 외부 에이전트 방(doc_talk)이 이미 SQLite에 있습니다. 별도 채팅 테이블을 복제하지 않고 통합 조회 모델과 사람 개입 API만 더합니다.
검토 항목 현재 상태와 구현 방식 (코드 근거)
1. DB 저장 현황과
누락·삭제 지점		 에이전트 간 메시지는 messages 테이블에 본문(body), 보낸 노드(sender·sender_name), 받는 노드(recipient), 전달 방식(kind: queue/steer/interrupt), 메시지 종류·답장 연결(what JSON 안 Answer.question), 읽음(delivered)이 들어 있습니다. 근거: src/db.rs:38-55, 206, 299, 397, api/src/graph/messages.rs:88-175 단, 세 가지 빈틈이 있습니다. ① 생성 시각 컬럼이 없습니다: messages.sent_at은 생성 시각이 아니라 노드에 넘긴 시각입니다(INSERT 시 NULL, src/graph/mailbox.rs:332, 930). created_at 컬럼 1개를 더해야 합니다. ② 노드를 지우면 받은 메시지가 연쇄 삭제됩니다: recipient가 ON DELETE CASCADE입니다(src/db.rs:40, src/graph/nodes.rs:271, 1108). ③ events 테이블은 10,000건에서 오래된 행을 지우고(src/graph/events.rs:13, 116-119) 본문은 LEFT JOIN messages로 읽으므로 노드 삭제 시 본문이 함께 사라집니다.
2. 기존 채팅방과의
관계 (단일 상태)		 기존 채팅방(/rooms/<노드>)과 외부 에이전트(loom room send, Aside의 POST /api/rooms/{node}/outside)는 doc_talk 테이블(doc = 'room/<노드>')을 씁니다. 근거: src/daemon/rooms.rs:5-62, src/graph/doc_talk.rs:51-210, src/cli/room.rs:23-74 새 채팅 테이블을 만들지 않습니다. 채팅 모드는 messages와 doc_talk을 한 번에 읽어 병합합니다(doc_talk.message로 중복 제거). 기존 /rooms/<노드> 주소와 외부 에이전트 연동 계약은 그대로 유지합니다.
3. 사람의 중간 개입 현재 사람은 POST /api/rooms/{node}/talk로 일반 메모(queue)만 보낼 수 있고(src/daemon/rooms.rs:33-50), 대기 중 메시지의 steer 승격만 따로 있습니다(src/daemon/nodes.rs:123-128). 채팅 모드 입력창은 받는 노드(1개 또는 양쪽 모두)와 전달 방식(일반·조정·중단)을 명시해 보냅니다. 노드 1개를 고르면 그 노드만 from: human 메시지를 받아 불필요한 토큰을 쓰지 않습니다. 양쪽 모두를 고르면 두 노드 모두 같은 지시와 상대 노드 수신 안내를 받습니다. 외부 에이전트는 pull 방식(loom room read)이므로 사람 말은 loom 노드로 전달되고 방 기록에 남아 다음 read 때 외부 에이전트도 봅니다.
4. API 계약과
화면 변경		 API(모두 추가 전용, 기존 계약 깨짐 없음): GET /api/chat/threads, GET /api/chat/threads/{key}, POST /api/chat/send(origin::writes_from_page 보호). 실시간 갱신은 기존 GET /api/events WebSocket의 Recorded·NodesChanged를 재사용합니다. 근거: src/daemon.rs:233-250, tests/contract/released.txt, web/src/TalkThread.tsx 화면(web/src/): 기존 TalkThread.tsx 말풍선(사람=진한 말풍선, 외부 에이전트=연한 말풍선, 노드=흰 말풍선)과 EventConsole.tsx 종류 배지를 그대로 씁니다.
5. 예상 규모와
주요 리스크		 규모: 1인 워커 기준 웹 1차 2.5~4일(DB·조회 1일, API·계약 0.5일, 웹 UI 1~1.5일, 실측·검토 0.5~1일). GPUI 데스크톱(desktop/) 포팅은 별도 2~3일입니다.
리스크: ① 메시지 양 — exited·adopted·idle 등 시스템 알림이 많아 기본 필터에서 접고 50건 단위 페이지네이션을 씁니다. ② 토큰 비용 — 채팅 모드는 사람용 보기이며 에이전트 컨텍스트에 전체 기록을 넣지 않습니다(추가 토큰 0). ③ 외부 에이전트(Aside) 프라이버시·신뢰 — doc_talk·messages는 로컬 DB에만 남으며, 화면에 외부 에이전트 · Aside 배지를 유지하고 개입 API는 브라우저·앱(Origin 검사)에서만 허용합니다.
상단에서 「채팅」 모드 전환→ 스레드 선택 (에이전트 간 / 외부 에이전트)→ 종류 배지·외부 말풍선으로 흐름 확인→ 받는 대상·방식(일반/조정/중단) 선택 후 개입→ 대상 노드가 즉시 수신·응답

D1채팅 모드를 화면 어디에 둘까요?

A메인 화면 전환(그래프 ↔ 채팅 전체 모드)권장지금: 그래프와 별도 /rooms 탭 오가기 → 바뀐 뒤: 한 창에서 2단 스레드 목록·대화·개입 · 비용 보통(1~1.5일) · 위험 낮음 · 되돌리기: 전환 버튼 제거
B오른쪽 도크에 [채팅] 탭으로 추가지금: 도크 4개 탭 → 바뀐 뒤: 그래프와 나란히 채팅 확인(스레드 목록은 드롭다운) · 비용 작음(1일) · 위험: 긴 대화·다수 스레드 읽기 불편 · 되돌리기: 탭 제거
  • 에이전트 간 통신과 외부 에이전트 방을 여러 스레드로 오가며 읽으려면 목록과 대화가 나란히 보여야 합니다.
  • 기존 오른쪽 도크(받은편지함·기록·문서·터미널)는 그대로 남아 필요할 때 옆에서 열 수 있습니다.

D2스레드 목록을 어떤 기준으로 묶을까요?

A노드 쌍(A ↔ B) + 외부 에이전트 방 단위권장지금: 이벤트 콘솔에 모든 메시지가 섞임 → 바뀐 뒤: 대화 당사자별로 분리 · 비용 작음 · 위험: 노드가 많으면 목록이 길어져 필터 필요 · 되돌리기: 조회 그룹 키 변경
B작업(루트 노드 트리) 단위 1개 단체방지금: 이벤트 콘솔 전체 → 바뀐 뒤: 한 작업의 모든 노드가 1개 방에 모임 · 비용 작음 · 위험: 코디·워커·검토자 대화가 한 방에 섞여 개입 대상이 흐려짐 · 되돌리기: 조회 그룹 키 변경
  • 노드 쌍 기준이면 대화 맥락과 사람의 개입 대상(A, B, 양쪽)이 바로 대응됩니다.

D3사람 개입 시 대상 선택과 전달 방식을 어디까지 열까요?

A대상(노드 1개 또는 양쪽 모두) + 방식(일반·조정·중단)권장지금: /rooms 일반 메모 1개만 가능 → 바뀐 뒤: 대화 중 바로 조정·중단 개입 · 비용 보통(0.5일 추가) · 위험: 실수로 중단 선택 시 턴 끊김(중단 시 경고색 강조) · 되돌리기: 방식 선택 숨김
B대상 1개 + 일반 메모만(기존 채팅방과 동일)지금: /rooms와 같음 → 바뀐 뒤: 일하는 중인 노드에 즉시 개입 불가 · 비용 작음 · 위험: 개입 체감이 약함 · 되돌리기: 나중에 확장 가능
  • 에이전트가 잘못된 방향으로 돌 때 채팅을 보다가 바로 조정(--steer)이나 중단(--interrupt)으로 개입할 수 있습니다.

D4병합 후 지운 노드의 대화 기록을 남길까요?

A남긴다(recipient 연쇄 삭제 해제 + recipient_name 저장)권장지금: 노드 삭제 시 받은 메시지 전부 소실 → 바뀐 뒤: 끝난 작업 대화도 다시 확인 · 비용 작음(DB 마이그레이션 1개) · 위험: DB 크기 서서히 증가 · 되돌리기: 오래된 기록 정리 작업 추가
B살아 있는 노드의 대화만 보인다(현재 삭제 방식 유지)지금: 노드 삭제 시 소실 → 바뀐 뒤: DB 변경 최소(created_at만 추가) · 위험: 워커가 자동 회수되면 대화가 사라짐 · 되돌리기: 추후 마이그레이션 가능
  • loom은 병합이 끝난 워커 노드를 자동으로 지우므로 연쇄 삭제를 풀지 않으면 작업 직후 대화 기록이 비게 됩니다.
