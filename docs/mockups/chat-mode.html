loom 채팅 모드: 타당성 검토와 화면 목업

사람 수정 요청(v2): “채팅모드에서는 각 에이전트의 세션도 cli 형식이 아닌 chat ui로 표시되며, 에이전트간 통신은 둘(또는 더 많이) 사이의 채팅방으로 표현되는 방식으로 목업수정”. v2에서는 ① 둘 이상이 함께 대화하는 그룹 채팅방(외부 에이전트 포함), ② 각 에이전트의 개별 세션을 말풍선·접힌 도구 호출 카드로 보여주는 1:1 세션 채팅 화면(터미널 전환 포함), ③ 세션 기록 출처·입력 전달 방식별 타당성과 결정 사항 5건(D1~D5)을 반영했습니다.

타당성 검토 요약 v2 · 에이전트 세션 채팅 UI 포함

단계 구현 가능 · 1단계 그룹방 2.5~4일 / 2단계 세션 UI +4~6일 에이전트 간 통신(messages)과 외부 방(doc_talk)은 즉시 통합할 수 있고, 주요 에이전트(Claude·Codex·Cursor·Pi/OMP)는 이미 loom이 세션 기록 경로 또는 서버 연결을 쥐고 있습니다.
검토 항목 현재 상태와 구현 방식 (코드 근거)
1. 에이전트 간 통신 DB와
그룹 채팅방		 messages 테이블에 본문(body), 발신(sender·sender_name), 수신(recipient), 방식(kind), 종류·답장(what JSON)이 들어 있습니다(src/db.rs:38-55, 206, 397). 작업 트리(부모-자식-검토자)와 doc_talk(room/<노드>)을 묶으면 2명 이상이 참여하는 그룹 채팅방을 새 테이블 없이 조회할 수 있습니다. 보강 필요: ① messages.sent_at은 넘긴 시각이라 생성 시각(created_at) 컬럼 1개가 필요합니다(src/graph/mailbox.rs:332, 930). ② recipient가 ON DELETE CASCADE여서 노드 삭제 시 메시지가 지워집니다(src/db.rs:40, src/graph/nodes.rs:271, 1108). ③ events는 10,000건 상한이 있고 본문을 LEFT JOIN messages로 읽습니다(src/graph/events.rs:13, 104-119).
2. 에이전트 1:1 세션
채팅 UI 기록 출처		 loom은 이미 nodes.session에 각 에이전트의 세션 기록 경로 또는 ID를 저장합니다(docs/design/에이전트-실행.md:211). • Claude Code · OpenClaude: transcript_path JSONL과 훅(last_assistant_message) (src/profile/claude.rs:509-545)
• Codex · Trae: codex app-server의 thread/read·턴/항목 목록·스트리밍 알림 (src/profile/codex/server.rs:481, src/profile/codex.rs:309)
• Cursor: agent-transcripts/<id>.jsonl(transcript_path)과 훅 (src/profile/cursor.rs:439, 479)
• Pi · OMP: --session JSONL 파일과 확장 이벤트 (src/profile/pi-loom.ts:137)
• OpenCode 2 계열: 전용 서버 HTTP·SSE 이벤트 (src/profile/opencode2/)
• 미지원 프로필(Crush SQLite, Hermes DB, DSH zstd, Vibe 저널, Antigravity·Copilot ID 전용, 셸 노드): 구조화 기록이 없으므로 기존 터미널 보기로 자동 폴백합니다. 누락된 부품: 프로필별 JSONL·서버 항목을 공통 항목(사람·응답·도구 호출·생각·상태)으로 바꾸는 파서와 파일 변경 테일러(대용량 세션 가상 스크롤 포함)가 필요합니다.
3. 사람 입력 전달 방식
(PTY 유지 vs 헤드리스)		 현재 노드는 PTY 안의 TUI로 돌고(src/node_host/host.rs), 사람은 터미널 입력·받은편지함·채팅방(POST /api/rooms/{node}/talk)으로 말합니다. 채팅 모드 안에서 모든 개입(대상·전달 방식·미읽음 대기 메시지 수정·취소·터미널 전환)을 끝내도록 두어 그래프로 돌아가지 않게 합니다. 기본 전달은 일반(queue)이며, 방 전체 전송은 노드마다 1턴씩 소비함을 안내합니다. 외부 에이전트(pull 방식)를 고르면 조정·중단을 비활성화하고 이유를 표시합니다. • 방식 A (기존 PTY 유지 + 기록 파싱): 채팅 입력은 POST /api/chat/send(from: human, queue/steer/interrupt)로 보내고 화면은 JSONL·서버 기록을 읽어 그립니다. 기존 어댑터·PTY 호스트·권한 승인·[터미널 보기] 전환이 그대로 살아 있습니다.
• 방식 B (헤드리스 전환): claude -p --output-format stream-json, TUI 없는 codex app-server, cursor-agent -p --output-format stream-json으로 띄우면 토큰 단위 실시간 스트리밍이 깔끔하지만, 터미널 폴백과 대화형 슬래시 명령을 잃고 17개 어댑터 수명주기를 새로 짜야 합니다.
4. 기존 채팅방과의
관계와 API 계약		 기존 /rooms/<노드>, loom room send/read, Aside의 POST /api/rooms/{node}/outside는 그대로 유지합니다(src/daemon/rooms.rs, src/cli/room.rs). 새 API는 모두 추가 전용이라 tests/contract 깨짐이 없습니다: GET /api/chat/threads, GET /api/chat/threads/{key}, GET /api/nodes/{id}/session-chat, POST /api/chat/send(origin::writes_from_page 보호).
5. 단계별 규모와
주요 리스크		 규모: 1단계 그룹 채팅방·개입 2.5~4일 → 2단계 주요 4종(Claude·Codex·Cursor·Pi/OMP) 세션 채팅 UI +4~6일 → 3단계 헤드리스 모드 선택 시 +2~3주(웹 기준, GPUI 데스크톱 별도 2~3일).
리스크: ① 기록 형식 변경 — Claude·Cursor JSONL은 비공개 내부 형식이라 CLI 판이 오르면 파서를 맞춰야 합니다(미지원 시 터미널 폴백으로 안전망 확보). ② 대용량 JSONL — 10~80MB 세션은 끝에서 역방향 읽기·테일링이 필요합니다. ③ 실시간성 — JSONL은 턴·도구 경계에 써져 토큰 단위 스트리밍보다 한 박자 늦습니다(Codex·OpenCode는 즉시 스트리밍). ④ 토큰 비용·프라이버시 — 채팅방 보기는 사람 전용이며 지정한 노드만 메시지를 받습니다. 외부 에이전트(Aside) 글은 로컬 DB에만 남고 외부 에이전트 · Aside 배지로 구분합니다.
상단에서 「채팅」 모드 전환→ 그룹 채팅방(2명 이상·외부) 또는 1:1 에이전트 세션 선택→ 말풍선·접힌 도구 카드로 작업 확인→ 대상·방식(일반/조정/중단) 선택 후 개입→ 필요 시 [터미널 보기]로 즉시 전환

D1채팅 모드를 화면 어디에 둘까요?

A메인 화면 전환(그래프 ↔ 채팅 전체 모드)권장지금: 그래프와 별도 /rooms 탭 오가기 → 바뀐 뒤: 한 창에서 그룹방·1:1 세션·도구 카드 읽기 · 비용 보통 · 위험 낮음 · 되돌리기: 전환 버튼 제거
B오른쪽 도크에 [채팅] 탭으로 추가지금: 도크 4개 탭 → 바뀐 뒤: 그래프와 나란히 확인(목록은 드롭다운) · 비용 작음 · 위험: 도구 카드·긴 세션 대화 읽기 좁음 · 되돌리기: 탭 제거
  • 그룹 채팅방과 에이전트 1:1 세션(접힌 도구 카드·긴 응답)을 오가며 읽으려면 넓은 2단 레이아웃이 필요합니다.
  • 오른쪽 도크(받은편지함·기록·문서·터미널)는 그대로 남아 필요할 때 함께 열 수 있습니다.

D2에이전트 간 채팅방을 어떤 기준으로 묶을까요?

A그룹 채팅방(2명 이상 참여: 작업 트리·검토 라운드 + 외부 에이전트)권장지금: 이벤트 콘솔에 모든 메시지가 섞임 → 바뀐 뒤: 코디·워커·검토자·외부 에이전트가 한 방에 모여 흐름 파악 · 비용 작음 · 위험: 참여자가 많으면 대상 선택 필요 · 되돌리기: 그룹 키 변경
B1:1 노드 쌍(A ↔ B) 단위로만 분리지금: 이벤트 콘솔 전체 → 바뀐 뒤: 2명씩만 분리 · 비용 작음 · 위험: 코디-워커-검토자 흐름을 보려면 방 여러 개를 오가야 함 · 되돌리기: 그룹 키 변경
  • 사람 수정 요청(“에이전트간 통신은 둘(또는 더 많이) 사이의 채팅방으로 표현”)에 맞고, 작업 단위 맥락이 끊기지 않습니다.
  • 개별 노드와의 1:1 대화는 같은 목록의 「에이전트 1:1 세션」에서 바로 열 수 있습니다.

D3사람 개입 시 대상 선택과 전달 방식을 어디까지 열까요?

A단일 대상·일반 대기 기본 + 방 전체(턴 비용 안내)·조정/중단·미읽음 수정/취소권장지금: /rooms 일반 메모 1명만 가능 → 바뀐 뒤: 그래프 전환 없이 채팅 안에서 개입 완결(외부 에이전트는 조정·중단 비활성) · 비용 보통(+0.5일) · 위험: 중단 오선택 주의 · 되돌리기: 승격 버튼 숨김
B대상 1명 + 일반 메모만(기존 채팅방과 동일)지금: /rooms와 같음 → 바뀐 뒤: 일하는 중인 노드에 즉시 개입 불가 · 비용 작음 · 위험: 개입 체감이 약함 · 되돌리기: 추후 확장
  • 에이전트가 잘못된 방향으로 돌 때 채팅을 보다가 바로 조정(--steer)이나 중단(--interrupt)으로 개입할 수 있습니다.

D4에이전트 1:1 세션 채팅 UI를 어떻게 구현할까요?

A기존 PTY 유지 + 세션 기록(.jsonl·서버) 파싱, [터미널 보기] 전환 유지권장지금: PTY 터미널만 표시 → 바뀐 뒤: 주요 4종(Claude·Codex·Cursor·Pi/OMP)을 채팅 UI로 표시하고 미지원 시 터미널 폴백 · 비용 +4~6일 · 위험: JSONL은 턴/도구 경계 갱신 · 되돌리기: 파서 비활성화
B헤드리스 모드(claude -p stream-json, TUI 없는 codex app-server 등)로 전환지금: PTY TUI → 바뀐 뒤: 토큰 단위 스트리밍 가능하나 터미널 보기·슬래시 명령 상실 · 비용 +2~3주 · 위험: 17개 어댑터 수명주기 전면 변경 · 되돌리기: 어려움
  • 방식 A는 기존 PTY 호스트·계정 전환·권한 승인·터미널 폴백을 깨지 않고 점진적으로 채팅 UI를 올릴 수 있습니다.
  • 향후 필요하면 어댑터 단위로 헤드리스 스트리밍을 선택 적용할 수 있습니다.

D5병합 후 지운 노드의 대화 기록을 남길까요?

A남긴다(recipient 연쇄 삭제 해제 + recipient_name 저장)권장지금: 노드 삭제 시 받은 메시지 전부 소실 → 바뀐 뒤: 끝난 작업의 그룹 채팅방 기록도 유지 · 비용 작음(마이그레이션 1개) · 위험: DB 크기 서서히 증가 · 되돌리기: 오래된 기록 정리 작업 추가
B살아 있는 노드의 대화만 보인다(현재 삭제 방식 유지)지금: 노드 삭제 시 소실 → 바뀐 뒤: DB 변경 최소(created_at만 추가) · 위험: 워커가 자동 회수되면 그룹방 대화가 빔 · 되돌리기: 추후 마이그레이션
  • loom은 병합이 끝난 워커 노드를 자동으로 지우므로 연쇄 삭제를 풀지 않으면 작업 직후 그룹 채팅방 기록이 비게 됩니다.
